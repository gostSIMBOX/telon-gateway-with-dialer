## Context

The application needs to support voice calls in various environments:
- Users with standard cellular service (GSM/3G/4G/5G)
- Users with internet connectivity but poor/no cellular signal
- Users who need to make international calls cost-effectively
- Enterprise deployments with private SIP infrastructure

**Key Forces:**
- Cellular calls require SIM card and cellular signal
- VoIP calls require internet connectivity and SIP account
- Different markets have different connectivity patterns
- Some users may prefer one method over the other
- Cost considerations: VoIP can be cheaper for international calls

---

## Decision

**Enable both native telephony (Tele) and SIP-based VoIP (Pjsip) in parallel.**

### Path Characteristics

| Aspect | Tele (Native) | Pjsip (VoIP) |
|--------|---------------|--------------|
| **Network** | Cellular (SIM) | Internet (WiFi/Data) |
| **Protocol** | Standard telephony | SIP/RTP |
| **Account** | Mobile carrier | SIP provider |
| **Credentials** | SIM card | Username/Password |
| **Availability** | Requires cellular signal | Requires internet |
| **Cost** | Carrier rates | SIP provider rates |
| **Quality** | Network-dependent | Bandwidth-dependent |
| **Emergency** | Supports emergency calls | No emergency calling |

## Consequences

### Positive

1. **Flexibility:** Users can choose call method based on availability and cost
2. **Redundancy:** If cellular signal is weak, VoIP may still work (and vice versa)
3. **Cost Optimization:** International calls can route via SIP for lower costs
4. **Enterprise Integration:** Can integrate with corporate SIP infrastructure
5. **Future-Proof:** Can deprecate one path without rewriting the other

### Negative

1. **Complexity:** Two parallel systems to maintain and debug
2. **Code Duplication:** Both paths need similar call control logic
3. **State Synchronization:** Must track which path each call uses
4. **UI Complexity:** UI must handle calls from both sources uniformly
5. **Testing Overhead:** Must test both paths independently

### Technical Debt Identified

1. **Hardcoded Credentials:** `pjsip.js` contains hardcoded SIP credentials
   - **Risk:** Security vulnerability
   - **Fix:** Move to secure storage (Keychain/Keystore)

2. **Dead Code:** `pjsip_old.js` is incomplete and unused
   - **Risk:** Confusion for maintainers
   - **Fix:** Remove file

3. **Event Handler Bug:** `call_changed` calls wrong callback
   - **Risk:** Call state updates trigger termination logic
   - **Fix:** Call `onCallChanged()` instead of `onCallTerminated()`

4. **Missing Coordination Logic:** No clear decision process for path selection
   - **Risk:** Unclear when to use which path
   - **Fix:** Document or implement routing logic

## Compliance

### When to Use Tele (Native)

- User has strong cellular signal
- Emergency calls (112, 911, etc.)
- User prefers cellular for cost/reliability
- No internet connectivity available

### When to Use Pjsip (VoIP)

- User has weak/no cellular signal but has internet
- International calls (cost optimization)
- Enterprise SIP infrastructure available
- User explicitly chooses VoIP option

## Implementation Notes

### Current State

Both modules are instantiated in `src/index.js`:
```javascript
this.tele = new Tele();
// this.pjsip = new Pjsip();  // Commented out - not currently used
```

**Observation:** Pjsip initialization is commented out, suggesting:
- Tele path is primary/active
- Pjsip path is disabled or under development
- Decision was made to use only Tele for now

### Event Unification Strategy

Both paths emit similar events but through different mechanisms:

**Tele:**
```javascript
DeviceEventEmitter.addListener('teleCallReceived', ...)
DeviceEventEmitter.addListener('teleCallChanged', ...)
DeviceEventEmitter.addListener('teleCallRemoved', ...)
```

**Pjsip:**
```javascript
endpoint.on("call_received", ...)
endpoint.on("call_changed", ...)
endpoint.on("call_terminated", ...)
```

**Recommendation:** Create unified event emitter that normalizes both sources:
```javascript
CallManager.on("call_received", (call, source) => {
  // source = 'tele' | 'pjsip'
})
```

## Alternatives Considered

### Alternative 1: Telephony-Only

**Decision:** Use only native telephony, remove SIP support.

**Pros:**
- Simpler architecture
- Single code path
- No credential management

**Cons:**
- No VoIP capability
- Limited to cellular coverage
- No cost optimization for international calls

**Rejected Because:** VoIP is a key differentiator for the product.

---

### Alternative 2: VoIP-Only

**Decision:** Use only SIP/VoIP, remove native telephony.

**Pros:**
- Single code path
- Full control over call experience
- Lower carrier dependency

**Cons:**
- No emergency calling
- Requires internet always
- Can't replace default dialer functionality

**Rejected Because:** Would lose native dialer integration and emergency calling.

---

### Alternative 3: Unified Abstraction Layer

**Decision:** Create single `CallProvider` interface with `TeleProvider` and `SipProvider` implementations.

**Pros:**
- Clean abstraction
- Easy to add new providers
- Consistent API

**Cons:**
- Significant refactoring required
- May over-engineer for current needs

**Deferred:** Can be implemented later if complexity grows.
